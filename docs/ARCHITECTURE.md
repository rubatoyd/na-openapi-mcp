# na-openapi-mcp 아키텍처 및 설계 의도

> 국회도서관 **자료검색** OpenAPI(`apis.data.go.kr/9720000/searchservice`)와
> **상세정보조회**(`.../detailinfoservice`)를 검색·대량수집하는 공통 코어(REST + MCP + CLI).
> 자매 프로젝트 `nl-openapi-mcp`·`kci-openapi-mcp`·`scienceON-mcp` 와 레이어 구성을 맞춘다.

---

## 1. 레이어 구조

```
server.py / cli.py         ← MCP 도구 · CLI 표면 (@_safe · annotations · 쿼터 가드)
        │
     client.py             ← HTTP · 페이징 · 재시도 · **절단 메타 산출**
        │
     parser.py             ← XML 봉투 파싱 · 오류코드 분류 · 봉투/값에서 자격증명 제거
        │
     models.py             ← Record 스키마 · name/value 매핑 · 하이라이트 제거 · 안내문 판정
        │
   exporters.py            ← xlsx / csv / json / sqlite
```

`config.py` 는 모든 층이 참조한다(엔드포인트 · 상한 · 화이트리스트 · census 상수 ·
자격증명 · `use_os_trust` · 로그 scrub).

## 2. 설계 결정과 그 이유

### 2-1. 검증기는 **정규화한 문자열을 돌려주고**, 호출자는 그것을 전송한다

검증만 하고 원문을 보내면 ` 전체 ,교육` 같은 입력이 통과한 뒤 서버에서 검색항목이
인식되지 않아 **전체 카탈로그 1,300만 건**이 온다. 실제로 그렇게 만들었다가 적대적
리뷰에서 잡혔다. `validate_search()`·`validate_detail_search()` 의 반환값을 쓰지 않으면
결함이 되살아나므로 회귀 테스트로 고정했다.

### 2-2. 화이트리스트는 **호출 전 방어선**이다

이 API 는 미지원 검색항목을 오류로 알리지 않는다(§ README ①). 사후 탐지
(`looks_like_ignored_search`)는 2차선일 뿐이고, 1차선은 반드시 호출 전이어야 한다.
`/detail` 쪽은 반대로 ERR04 로 실패하는데, **그 코드가 일시 오류와 같아** 재시도를
낭비하므로 역시 호출 전에 막는다.

### 2-3. 절단은 **데이터가 아니라 메타로** 전달하고, **원인별로 분리**한다

레코드만 돌려주면 호출자가 `total` 을 볼 방법이 없고, 그 순간 부분 집합을 전수로
오인한다(자매 프로젝트 2곳에서 실제 발생). 신호를 나눈 이유는 **처방이 다르기 때문**이다:

| 신호 | 처방 |
|---|---|
| `truncated` | `max_records` 상향 |
| `cap_hit` | 상향해도 안 됨 — 검색식 분할 |
| `early_stop_note` | 중복 응답·서버 이상 조사 |
| `stopped_early_note` | 예산 배분 재조정 |
| `zero_yield_warning` | 다른 검색항목 사용 |
| `option_ignored_warning` | `dbname` 함께 지정 |

⚠️ **회수 한계는 상수가 아니다** — `pageno 최대 99 × page_size` 다. 상수 99,000 으로
판정하면 `page_size` 를 낮췄을 때 못 받는 구간을 받을 수 있다고 보고한다.

### 2-4. 원본을 버리지 않는다

`Record.raw` 에 응답 name/value 를 통째로 보존한다. 정규화는 손실 변환이고, 이 API 는
자료종마다 필드 이름이 갈리며(표제만 9가지) 값 자리에 안내문이 오기도 한다.
안내문으로 비운 필드는 `placeholder_fields` 에 이름을 남겨 **'미입력'과 '안내문'을
구분**할 수 있게 한다 — 그 구분이 없으면 E-BOOK 의 DDC 99.95% 가 결측으로 보인다.

### 2-5. 정제는 **화이트리스트로 좁힌다**

`clean_html` 이 임의의 `<…>` 를 지우면 데이터가 깨진다 — 이 카탈로그는 표제에 꺾쇠를
실제로 쓴다(`<표 124> …`, 표,그림DB 는 거의 전부). 초판이 그렇게 만들어 라이브 표본
1,000건 중 18건의 표제가 손상됐다. 지우는 태그를 이름으로 한정한다.
같은 이유로 `is_placeholder` 도 부분일치가 아니라 **값 전체 일치**로 판정한다.

### 2-6. 실패는 층마다 다르게

- `server.py` 는 `mcp.server.fastmcp` 를 **조건부 import 하지 않는다** — 폴백을 두면
  의존성 상한 누락이 감춰지고 반쯤 동작하는 서버가 뜬다(자매 3곳의 실제 결함).
- `parser` 는 첫 페이지의 `result` 부재를 **오류로 본다** — 빈 목록 통과는 태그명 변경
  (`recode`↔`record`) 같은 사고를 '결과 0건'으로 둔갑시킨다.
  단, **끝을 지난 페이지는 정상적으로 비어 있으므로** 호출자가 문맥(`expect_records`)을 준다.
- 반대로 **MCP 도구 경계에서는 조용하게** — `@_safe` 가 모든 예외를 dict 로 바꾼다.
  프로토콜 밖으로 예외가 새면 클라이언트가 깨진다.

### 2-7. 인증키는 **한 곳에서만** URL 에 붙인다

`config.build_url()` 이 유일한 결합 지점이다. `params=` 로 넘기면 이중 인코딩되어
조용히 인증 실패하므로, 실수할 자리를 구조적으로 없앤다.
누출 경로는 세 겹으로 막는다 — `raise_for_status()` 미사용(예외에 URL 이 박힌다),
파서가 봉투·레코드 값에 `scrub()` 적용, 로깅 필터(urllib3 가 DEBUG 에서 전체 URL 을 찍는다).

### 2-8. 쿼터는 **호출 전에** 지킨다

개발계정은 10,000건/일인데 `na_collect(terms=[…50개], max_records=10**9)` 은 최대
4,950회를 태울 수 있었다. 예상 호출 수를 먼저 계산해 상한을 넘으면 거부한다 —
실행하고 후회하는 것보다 낫다.

### 2-9. TLS·venv

`config.use_os_trust()` 를 `NaClient.__init__` 에서 호출한다. MCP 등록 명령줄에 두면
`.mcpb` 번들·PyInstaller 바이너리 경로에 적용되지 않아 교육망에서 실패한다.
venv 는 클라우드 동기화 폴더 밖에 둔다(자매 3곳 모두 `pyvenv.cfg` 파손을 겪었다).

## 3. 측정 방법론

이 저장소의 API 사실은 전부 라이브 왕복으로 확정했고, 탐침 스크립트로 재현 가능하다.

| 스크립트 | 확인하는 것 |
|---|---|
| `probe_api.py` | 엔드포인트 생존 · 키 인코딩 판별(대조군 포함) · 봉투 구조 |
| `probe_limits.py` | `displaylines`·`pageno` 상한 · 검색항목 폴백 · dbname × 항목 전수 · 하이라이트 오염 필드 |
| `probe_fields.py` | 자료종별 필드 census(채움률 · 안내문 · 연도 형식) |
| `probe_discover.py` | **목록 밖** 검색항목 발견 — 관측된 레코드 필드명을 후보로 사용 |

**규율 셋** (전부 값을 치르고 얻었다):

1. **소표본으로 단정하지 않는다.** 자료종당 30건으로 낸 결론이 1,300건 재측정에서
   10건 뒤집혔다. 원인은 **무필터 검색이 깊이 500건까지 최신 연도로 채워지는 것** —
   층화 없이는 무엇을 재도 '신착의 실태'만 나온다.
2. **ERR04 는 재시도한 뒤에 판정한다.** 간헐적이라 1회만 태우면 멀쩡한 항목이
   '거부'로 기록된다(`세미나자료/전체항목` 이 실제로 그렇게 오판됐다).
3. **후보 집합이 자기 출력이면 재현이 아니다.** `DB_CATEGORIES` 만 후보로 쓰면 이미
   걸러진 목록을 다시 확인할 뿐이다. `probe_discover.py` 가 관측 어휘로 그 밖을 탐색한다 —
   다만 관측되지 않는 이름은 여전히 못 찾는다는 한계가 있다.

## 4. 대량 수집 흐름

```
na_collect(terms=[…])
   → 쿼터 가드(예상 호출 수 상한 확인)
   → 검색어별 search_meta()        … 각각 최대 99 × page_size
   → 제어번호 기준 합집합           … axes[] 에 검색어별 total·fetched·new 기록
   → 연도·contains 로컬 후처리      … 필터링 건수를 meta 에 집계
   → exporters.export()            … 형식은 **쓰기 전에** 전부 검증
   → 경고를 최상위로 승격           … axes 안에만 있으면 호출자가 못 본다
```

`|` 가 AND 이므로 **OR(합집합)은 클라이언트에서** 만든다.
`max_records` 는 **검색어 전체에 걸친 예산**이라, 앞 검색어가 다 쓰면 뒤 검색어는
조회되지 않는다 — 그 사실을 `terms_unsearched`·`stopped_early_note` 로 반드시 알린다.
